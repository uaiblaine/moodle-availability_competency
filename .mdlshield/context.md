# Review context for availability_competency

`availability_competency` is a Moodle availability condition ("Competency"). It restricts
access to an activity or a course section until the learner is, or is not, proficient in one
competency, read from the learner's course rating or from the site-wide rating. It supports
Moodle 4.5 through 5.2 on one branch. **It defines no database tables, capabilities, web
services or page scripts**: the condition is stored as JSON in core's
`course_modules.availability` and `course_sections.availability`, and the ratings it reads
belong to core competencies.

## Who is trusted

- Site administrators are fully trusted.
- Whoever core allows to edit an activity's or a section's restrictions can add this
  condition; the plugin adds no check of its own there. That is course-level editing rights
  (core's `course/modedit.php` and `course/editsection.php` decide; sections need
  `moodle/course:update`), not a competency capability.
- The only admin setting is `cleanuponcompetencydeletion`, a checkbox that defaults to off.
- Learners, guests and any user evaluated by cron are untrusted callers of `is_available()`.
  Competency short names are set by users who manage competencies and are treated as
  markup-bearing input wherever they are printed.

## Surfaces

- `classes/condition.php`: `is_available()` reads `competency_usercompcourse` (scope `course`)
  or `competency_usercomp` (scope `global`) directly, plus the competency short name. It
  writes nothing. Results are cached in static arrays for at most 60 seconds or 1000 entries.
- `classes/frontend.php` feeds the YUI form (`yui/src/form/js/form.js`, built into
  `yui/build/`) with the competencies linked to the course and those named by the item's
  stored conditions. Names reach the form already passed through `format_string()`.
- `db/events.php` registers two observers. `competency_evidence_created` only empties the
  static caches. `competency_deleted` queues one adhoc task per competency, only when the
  cleanup setting is on; the task rewrites `availability` in every module and section of the
  site that holds a `competency` condition, and logs each previous value.
- `cli/report_conditions.php` is a read-only report of restrictions that name no usable
  competency; it takes no user input beyond `--problem`.
- A restriction message names the competency by its short name, HTML-safe, to anyone the
  message is shown to.
- Privacy provider: `null_provider`. No file serving, no outbound HTTP, nothing evaluated
  from user input.

## Facts that look like findings but are by design

- **The condition reads rating tables directly instead of `\core_competency\api`.** The API
  getters check the current user's capabilities, throw exceptions that core's
  `info::is_available()` does not catch (it catches only `coding_exception`), and
  `get_user_competency_in_course()` inserts a row on read. A call to those getters from
  evaluation is a finding. Pinned by `condition_test::test_guest_does_not_break_the_course_page`,
  `test_prohibited_competency_view_does_not_break_the_course_page` and
  `test_evaluation_writes_no_record`.
- **Evaluation ignores the course link, the framework's context and whether competencies are
  enabled.** Linking is only the authoring filter; a stored rating keeps counting so a learner
  already rated proficient keeps access (`test_rating_counts_after_unlinking`).
- **A competency that does not exist counts as not proficient**, so a "not proficient"
  condition on it is met. JSON without `scope` is read as `course`.
- **A restore never drops a condition.** Dropping it would open the item to everyone. From
  another site with no mapping, the condition is pointed at competency 0 and a warning is
  logged; on the same site the ID is kept.
- **The cleanup walks the stored JSON by hand** because core has no API to remove one
  condition from a tree. The `LIKE '%"competency"%'` is only a prefilter; removal is decided
  by `type` and ID, through negated operators, and only conditions that can never be met are
  removed so no item loses access. The result is verified before it is written
  (`observer_test` covers nesting, negation and sections).
- **The form concatenates names into HTML on the client.** That is safe only because the
  server sends `format_string()` output; a raw short name reaching the form is a finding
  (`frontend_test` pins `Beta &amp; gamma`).

## De-emphasise

- `yui/build/**` is generated by the Moodle shifter from `yui/src/**`; review the source.
- `lang/**`, `tests/**`, `docs/**` and `CHANGELOG.md` carry no production behaviour.
- The CI workflow lists one job per supported Moodle branch on purpose.
